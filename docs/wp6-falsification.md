TB-05 SURVIVED on its first run. The barrier held the customer row `FOR UPDATE`, and the
override's own foreign-key check takes `KEY SHARE`, which that holder also blocks — so a
version with no customer lock waited anyway. The holder now takes `FOR NO KEY UPDATE`,
which conflicts with `lockCustomer`'s `FOR UPDATE` and not with the key check; the row
above is the re-run. The other four tests that die under TB-05 do so because the
replacement call is not a lock, not because they test it.

TB-17 had no row until the two-resets race test was written, because nothing killed it.
Without `reset_at IS NULL`, the reset that waited re-stamps both grants with its own id
and records a second reset for the same consumption. No single-transaction test can see
this: a grant only carries another reset's stamp once a concurrent reset has committed it.
