## Notable UI/methodology patterns (not business rules, but relevant to future field testing and to the eventual panel-rebuild)

- **UI-PATTERN-001**: Most Edit-Product fields present their choices as actual reply-keyboard/inline buttons (one tap = one value). The exception found so far is `رنگ محصول` (Product color), whose prompt LISTS 4 style keywords (`danger`/`success`/`primary`/`default`) as plain descriptive text with no attached buttons at all — the admin must type one of the literal English keywords as free text. Do not assume "options listed in a prompt" implies clickable buttons; verify each field individually (relevant especially for the still-untested `تنظیم اینباند`, `محدودیت کاربر`, `ایموجی پریمیوم محصول`).
- **UI-PATTERN-002**: Selecting a real, production entity (e.g., a real category) as the VALUE of a TEST record's own reference field (e.g., TEST_STORE_PRODUCT's `دسته بندی`) only ever writes to the TEST record's own foreign-key/reference — it does not modify the real entity itself in any way. Confirmed directly via INCIDENT-002. This is reassuring for the safety boundary but does NOT license casually selecting real entities — it was an accident, not a technique, and is only mentioned here for completeness.
- **UI-PATTERN-003**: Not every field-edit confirmation reprints the full "ویرایش محصول" summary + keyboard (e.g., رنگ محصول's confirmation didn't). When the keyboard disappears, `/start` reliably resets to the root menu, from which تنظیمات فروشگاه → مدیریت محصولات → ویرایش محصول → (location filter) → (user-type filter) → product name re-enters Edit Product. Typing a persistent-keyboard button's exact label as free text (e.g., `پنل مدیریت`) was tried once and did NOT get a bot reply — do not rely on this shortcut; use `/start` and the full menu chain instead.
- **UI-PATTERN-004 (blocking issue, unresolved)**: After a tool/browser reconnect, the 18-field Edit-Product reply-keyboard sometimes fails to render in Telegram Web at all — confirmed via direct DOM inspection (no element anywhere on the page contains the field labels, so it is not a rendering/visibility bug, the keyboard is genuinely not attached client-side). In this state, free-text guesses at field names fail silently (no bot reply, no error) unless the EXACT string the bot expects is sent, and that exact string cannot be reliably reconstructed from the field's DISPLAY emoji in the summary (e.g. the summary shows "👤 محدودیت کاربر" but sending "👤 محدودیت کاربر" got no response) or from a bare Persian label without its button's own emoji (e.g. bare "ویرایش محصول" failed; "✏️ ویرایش محصول" — emoji sourced from prior documentation, not guessed — succeeded). This blocked testing of `محدودیت کاربر`'s actual value, `تنظیم اینباند`, `مخفی کردن پنل`/`حذف کلی پنل های مخفی`, and `ایموجی پریمیوم محصول` this session. Recommended fix for next attempt: re-enter Edit Product and screenshot/DOM-check immediately, before sending any other message, to catch the keyboard while it's live; do not attempt to reconstruct button text from memory.
