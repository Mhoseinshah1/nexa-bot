### Purchase Session (ephemeral, Telegram-side only)
Not a named entity anywhere in project-knowledge/ — INFERRED as a conversational-state concept: the bot tracks "what free-text reply are we expecting next" (a GB number, a day count, a discount code) without any visible session/cart identifier shown to the user. Observed stages, VERIFIED_BY_TELEGRAM across purchase-flow.md, renewal.md, extra-traffic-time.md, and services.md's transfer-prompt:
`Category select → Product/volume select (or custom-service's 2-step free-text volume+duration prompt) → Checkout message (price shown, order/service username pre-generated) → [Payment-method choice — NOT reached this phase] → (presumed) Provisioning`
Once a checkout message is shown, a username/short-ID (`{short_id}_{user_id}` format, matching the subscription-link pattern) is ALREADY assigned — VERIFIED_BY_TELEGRAM from the custom-service checkout (purchase-flow.md Step 2b) — meaning some backing record (likely an Order/Invoice row) is created at checkout-message time, BEFORE any payment confirmation. This is a significant state-model finding: "checkout shown" is itself a state transition with a side effect, not a pure read.
Back/Cancel behavior: every checkout observed offers a "🏠 بازگشت به منوی اصلی" button that returns to the bare home state with no visible cancellation confirmation or "order voided" message — VERIFIED_BY_TELEGRAM, consistent across purchase/renewal/extra-volume/extra-time/custom-service.
Admin Relationship: likely maps to project-knowledge/entities.md Order/Invoice entity's earliest lifecycle state (pre-"Unpaid", or an initial "Unpaid" row itself — UNK-T003, not confirmed which).

### Order / Invoice
Telegram-visible evidence only (no direct field-by-field admin cross-check this phase):
- A checkout message = an Order/Invoice-like record exists with: username/short-ID, service name/label, duration, price, volume (if applicable), an optional note field (empty by default), and the requesting user's live wallet balance shown alongside it (VERIFIED_BY_TELEGRAM, purchase-flow.md, extra-traffic-time.md).
- "My Services" (/services) never lists a service tied to an abandoned/unpaid checkout — VERIFIED_BY_TELEGRAM, cross-checked (purchase-flow.md, services.md) — confirms provisioning (and hence "Service" existence) is GATED on payment, consistent with project-knowledge/orders.md BR-013. The Order/Invoice row itself may or may not exist server-side in an Unpaid state regardless (UNK-T003, unresolved — would need Admin Panel access).
- "تعداد فاکتورهای پرداخت‌شده" (paid-invoices count) on /wallet is strictly ≥ "تعداد سرویس‌های خریداری‌شده" (purchased-services count) for this real account (8 vs 1) — INFERRED that "Invoice" is a broader concept spanning services, renewals, and add-on purchases (extra-volume/time), while "Service" only increments on a fresh product purchase, not on renewals/add-ons of an EXISTING service.
State transitions inferred (not all directly observed): `(created at checkout) → Unpaid → [payment] → Paid/Provisioned` — the middle transition (payment) was never completed this phase (by design, per the safety rules), so the Paid state's exact Telegram-visible signal (a confirmation message? a "service ready" notification?) is UNKNOWN/NOT_TESTED.
