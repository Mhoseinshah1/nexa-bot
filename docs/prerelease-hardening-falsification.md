# Pre-release hardening — falsification record

The rules are those of `docs/prerelease-hardening-audit.md`. Each was reverted alone, with an exact string replacement, in `/home/user/nexa-hard` against its own database (`nexa_hard`), with no other suite running.

- **Which tests ran.** Only the named tests, selected with vitest `-t` on their titles.
- **Restoring.** The original file content was written back after each row. `git status` was clean at the end of the pass.
- **Counting a kill.** A row counts as killed only when vitest exited non-zero AND listed a named test as failed. A run that executed no test does not count.
- **Package rows.** `@nexa/contracts` and `@nexa/i18n` resolve to their built `dist/`, so a mutation under `packages/` counts only when both packages were rebuilt after it and again after the restore.

The first pass over PRH-09…PRH-14 did not rebuild. All six "survived" because the tests never saw the mutation. PRH-14 also "survived" because its `-t` filter matched no test title. Both passes are discarded and the rows below are the re-run. This is recorded because a green run that executed nothing is the failure this procedure exists to catch.

**15 killed, 3 survived.** None of the three survivors is counted as a kill.

- **PRH-05 and PRH-06 survive by construction.** Each surface admits a decision only for a payment with a receipt:
  - the `D:` path through the review item's guard (PRH-01);
  - the reject path through the capture's `admitted` (PRH-04).
    `payment_receipts` refuses DELETE, so a receipt seen at admission is still there when the service decides. The `requireReceipt` flag is therefore the second statement of a rule already held. Its own check is pinned by PRH-02 and PRH-03, which call the service with the flag and no receipt. It is kept because the service is the layer that writes, and it is what a future caller that skips the surface would meet.
- **PRH-16 survives because the outcome is the same.** Without the early answer, the waiting confirmation redeems from the locked row. It inserts nothing, because `discount_redemptions_order_discount_key` holds one redemption per (order, rule). It then loses the conditional `DRAFT → AWAITING_PAYMENT` UPDATE (`changed: false`, so no `OrderConfirmed`), and it returns the same order. The early answer skips that redundant work, and the test pins the outcome both versions share.
