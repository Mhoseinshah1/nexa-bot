# RickPanel NEW_SERVICE hotfix — the create's `proxies` seed

A RickPanel-backed purchase took the customer's money, failed to create the account,
and refunded them. The cause was one missing field on the create. This file records
the evidence, the fix, what is still unproven, and the tests that hold it.

## 1. The defect

- **What the owner saw on the test runtime:** order settled, provisioning attempted,
  no provider user created, provisioning eventually failed, customer refunded.
- **What should happen:** purchase, then RickPanel create, then authoritative
  read-back, then `subscription_url`, then delivery persisted, then link sent.

## 2. The evidence

The owner's direct calls to a **correctly connected** RickPanel admin. The owner
reported them in the instructions for this work, which are not a repository file, so
the table below is the tracked record: every row is transcribed here in full, and
nothing in this document depends on a source a reader cannot open. None of it was
produced by this session. This session has no access to the test environment and
must not ask for its credentials.

The first row is the one the fix rests on, and it is stated precisely because it is
weaker than the rest. It is **not** a direct call with its status captured. It is the
bot's own NEW_SERVICE create, which omitted `proxies`, failing on the correctly
connected panel, set against the direct create that carried the seed and succeeded.
What status the panel used is not recorded: `OQ-RP-06`, §7.

| call                                                                                  | result                                                                                                                                                                |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the bot's NEW_SERVICE create, **without** `proxies`, on the same panel                | **failed**: no user created, the order eventually refunded. Status and body not captured (`OQ-RP-06`)                                                                 |
| token exchange                                                                        | works                                                                                                                                                                 |
| `POST /api/user` with username, future `expire`, `no_reset`, `proxies: {"vless": {}}` | **200**                                                                                                                                                               |

The shipped adapter omitted `proxies` from the create. It did so on purpose: its
docblock quoted the OpenAPI description, "`inbounds` and a partial `proxies` set are
accepted but ignored". That sentence is true of a **partial** set. It says nothing
about an **absent** one, and the panel refuses an absent one.

Two earlier results came from a **misconfigured** connection and are not generalised:
the disable/delete restrictions and the minimum-renewal refusal. Provider
policy can differ per admin or per service. The table above is the baseline.

## 3. The causal chain, and what could not be reproduced

**Reproduced here, against the corrected fake.** The fake now refuses an unseeded
create, as the owner's panel did. Against it, the shipped adapter could not create
any account: 10 of the 28 adapter tests failed before the fix, every one of them on a
create path. After the fix, all 34 pass.

**Not reproduced here: the real bot failure on the real panel.** This session
cannot reach the test environment, so the exact status the panel returns for the
unseeded create has not been captured. The code gives two readings, and both end in
the refund the owner saw:

- **400:** `PROVIDER_REFUSED`, terminal on the first attempt, and refunded at once.
- **422, or anything else unlisted:** `PROVIDER_ERROR`, which is UNKNOWN for a
  PROVISION. The service goes to `UNRECONCILED`. A RECONCILE reads the account, gets
  404, returns the service to PENDING_PROVISION, and re-plans the create, which is
  refused again. The cycle repeats until `SERVICE_PROVISION_CYCLE_LIMIT`, then
  `PROVISION_CYCLE_EXHAUSTED` refunds.

The second reading is **reproduced through the shipped container** by
`rickpanel-new-service.test.ts` › bounds a create the panel keeps answering 422. The
provisioner drains everything due in a single tick, so the whole cycle runs inside it.
The trail on the panel is `CREATE, READ, CREATE, READ, CREATE, READ`, the order ends
REFUNDED with exactly one refund, and later sweeps create nothing more.

That cycle is bounded and safe:

- no create goes out without a READ between it and the last one;
- nothing is refunded while the outcome is unknown;
- the refund happens once.

What it cannot do is succeed. That is why the seed, not a reclassification, is the
fix. Which status the real panel actually uses is still an inference ("eventually
refunded" fits the 422 reading better than 400), recorded as **OQ-RP-06**.

## 4. The fix

- **`RICKPANEL_CREATE_PROXY_SEED = {"vless": {}}`**, sent on every create
  (`rickpanel.adapter.ts`). It is the one shape measured on the real panel, and it is
  frozen.
  - Not customer- or operator-selected. No product, form, Telegram step or activation
    field reaches it, and `requiredActivationFields` stays `[]`.
  - Not a protocol restriction. The subscription is not VLESS-only; the panel
    generated records for several protocols.
  - Not a credential. The empty object asks the panel to generate one. Nexa never
    reads the generated credentials back out and never delivers them.
  - `inbounds` stays absent.
- **Create result handling was already right and is now held by tests at both
  layers.** The create is followed by a bounded read-back by the reserved username.
  It requires the record, takes `subscription_url` from the **read-back** (never from
  the create response), and never reports success without a link.
- **No classification changed.**
  - 400 and 403: `PROVIDER_REFUSED`, as before.
  - 409: `PROVIDER_REFUSED`, never adopted, as before. The stale docblock line that
    still said "read the user back and ADOPT it" is corrected (a name match never proves an account is ours), and so is the
    acceptance case A2, which still asserted adoption.
  - 429: `RATE_LIMITED`.
  - Everything else, 422 included: `PROVIDER_ERROR`, which is UNKNOWN and reconciled
    by a READ.
  - The owner's rule: 422 may be classified as a refusal only if a correct-panel
    reproduction proves it deterministic, and no other 4xx is generalised without audit. No such reproduction exists, so it is not done. The two
    possible mistakes cost different things. An ambiguous answer taken as a refusal
    could refund an account the customer is holding. A refusal taken as ambiguous
    costs a READ and, at worst, a delayed refund.
- **Entitlement (the owner's rule: never alter what was purchased to suit a panel).** The create sends exactly what the order froze: a limited cap
  as its bytes, unlimited as the panel's `0`, the expiry in epoch seconds, and never a
  default cap or an invented term. A refusal refunds the order under the existing
  exactly-once rules.

## 5. Tests

`tests/unit/rickpanel-adapter.test.ts`, against the corrected in-file fake:

- sends the fixed proxies seed and no inbounds
- is delivered by a panel that refuses an unseeded create with 400 / 422
- keeps a 422 on create UNKNOWN until real evidence classifies it
- creates a limited plan with exactly the traffic and expiry it was sold
- creates an unlimited plan as the panel unlimited, with nothing invented
- delivers the subscription link and none of the credentials the panel generated

`tests/integration/rickpanel-new-service.test.ts` runs through the shipped container
against `tests/support/fake-rickpanel.ts`. That covers the real provisioner, the real
adapter over the real `SafeHttpClient`, the ledger and the delivery lane:

- creates, reads back and delivers the link: one debit, one account, no refund
- creates a LIMITED plan with the traffic it was sold, and an unlimited one as 0
- refunds a rule refusal exactly once and never creates again
- reads before it creates again after an ambiguous create, and refunds nothing
- bounds a create the panel keeps answering 422: three rounds, READ between, one refund

`tests/acceptance/real-panel-rickpanel.test.ts` covers the real-panel side:

- A2 is corrected to assert refusal on 409.
- A7 is new: limited and unlimited plans read back by an independent observer.
- The suite has **not been run**. It needs a disposable panel, and this session has
  none.
