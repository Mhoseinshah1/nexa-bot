# Sanaei / 3X-UI — provider compatibility

## What this release claims

**Implemented and verified against the v3.7.0 wire contract.**

|                       |                                                                                                     |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| Provider              | MHSanaei/3x-ui                                                                                      |
| Evidence baseline     | `v3.7.0`                                                                                            |
| Exact upstream commit | `f727d04f6522bb94a8fb52e8352fdcafb51c11e1`                                                          |
| Auth verified         | Bearer API token; cookie session with CSRF                                                          |
| Health endpoint       | `GET panel/api/server/status`                                                                       |
| `webBasePath`         | supported                                                                                           |
| 2FA                   | never persisted or generated by Nexa; an API token is the recommendation for unattended integration |
| Preferred token       | least-privilege **monitor** scope, where the operator can create one                                |

Nothing here claims support for any other release. Behaviour was read from the
source at that commit, not inferred from a similar version, and the statements
below cite the file each one comes from. A different release may differ; if it
does, this document and the deterministic fake are the two places to change.

## What Phase 3B implements

The **connection half** only: authenticate, and read what the panel says about
itself. Creating clients, mutating inbounds, resetting traffic, delivering
subscriptions and scheduling background health are all later phases. The
descriptor's capability list describes the PROVIDER, exactly as Marzban's does;
the adapter interface it satisfies is `ProviderConnectionAdapter`, and
`IMPLEMENTED_PROVIDER_TYPES` is what states this release can actually operate a
`sanaei` panel.

## Authentication

v3.7.0 accepts two credentials on the same `/panel/api` surface
(`internal/web/controller/api.go`, `checkAPIAuth`), so Nexa models both.

### Selection is deterministic, and never falls back

```
panel.api_token configured            → Bearer mode
else panel.username + panel.password  → session compatibility mode
else                                  → panel.credentials_missing, nothing contacted
```

A configured API token that the panel REJECTS is an authentication failure. It
is never retried as a username and password. An operator who configured
token-only access — possibly a deliberately weak monitor token — must see that
token auth is broken rather than have Nexa quietly authenticate with the more
powerful credential they did not point at this job; a token typo would
otherwise silently escalate every future probe. The choice is made in the
credential resolver, which hands the adapter one already-narrowed shape, so no
adapter can implement the fallback even by accident. A deliberate fallback
would be a product policy decision and a change to that resolver.

### Mode A — Bearer (preferred)

```
GET panel/api/server/status
Authorization: Bearer <token>
X-Requested-With: XMLHttpRequest
```

One request. No CSRF round trip: `CSRFMiddleware`
(`internal/web/middleware/security.go`) short-circuits for a request
`checkAPIAuth` already authenticated, so asking for a token first would be a
wasted request against a panel that does not want one.

**Scopes.** v3.7.0 has three (`internal/database/model/model.go`): `admin`,
`monitor`, `node-sync`. `/server/status` is in the `monitor` allowlist for GET
and HEAD, and in the `node-sync` allowlist for GET (`enforceTokenScope`).
**Nexa does not need an admin token to monitor health** — prefer a `monitor`
token. A token whose scope does not reach the route is refused with HTTP 403
and an envelope, which Nexa reports as an authentication failure with that
status.

**Why `X-Requested-With` is sent.** `checkAPIAuth` answers an unauthenticated
API request **401** when that header is present and **404** when it is not.
Without it a rejected token arrives as a 404 — indistinguishable from a panel
served at a different base path — and "your token is wrong" would be reported
as "there is nothing there". Because the adapter always sends it, a 404 on this
path is the documented unauthenticated answer, and it is classified as an
authentication failure for that reason and no other. Arbitrary remote 404s
elsewhere are not treated as auth failures.

### Mode B — session with CSRF

`POST login` is **not** a bare call. It sits behind `CSRFMiddleware`
(`internal/web/controller/index.go`), so the sequence is:

1. `GET csrf-token` → `{"success": true, "obj": "<token>"}`, plus the `3x-ui`
   session cookie. `ValidateCSRFToken` (`internal/web/session/csrf.go`)
   compares the submitted `X-CSRF-Token` against the token stored **in that
   session**, so the cookie and the token are one unit.
2. `POST getTwoFactorEnable` with the same cookie and token → `{"obj": <bool>}`.
   Asked **before any credential is submitted**. This is a deliberate extra
   request: `defaultLoginLimiter` blocks an IP-and-username pair after enough
   failures, so discovering 2FA by submitting a login that cannot succeed would
   spend the operator's own lockout budget to learn it.
3. `POST login` with the same cookie and token, JSON `{username, password}`.
4. `GET panel/api/server/status` with the session cookie.

**HTTP 200 is not success.** A wrong username, a wrong password and a wrong 2FA
code all return HTTP 200 with `{"success": false, …}`. Every consumed response
is parsed for the `{success, msg, obj}` envelope and judged on `success`.

**The upstream `msg` is never repeated.** It is localized, and on a failed login
it is the panel echoing a decision about credentials just submitted. What
leaves the adapter is a failure kind, a status number, and a version string
that passed a character allowlist.

### 2FA

Nexa stores no TOTP seed, no OTP code and no reusable second factor, and there
is no `panel.totp_secret` credential. `twoFactorCode` is never sent.

When `getTwoFactorEnable` answers true and only a username and password are
configured, the probe stops with `AUTHENTICATION_REQUIRES_INTERACTION` — a
distinct failure kind precisely because the remedy differs from a rejected
password, and telling an operator to retype a correct password would feed the
login limiter. The remedy is to configure an API token. No login is attempted,
so nothing counts against the panel's lockout.

## `webBasePath`

`webBasePath` is a real upstream setting (`docs/content/docs/en/config/panel.mdx`),
normalized to `/…/`, and a hardened panel is routinely served under a long
random path. **Panel `baseUrl` is authoritative**, and every path the adapter
uses is relative with **no leading slash**:

```
csrf-token          getTwoFactorEnable
login               panel/api/server/status
```

A leading slash would discard the configured path under WHATWG URL resolution
and land on the origin root. Tested at `https://host/`,
`https://host/xui-secret-path/`, `https://host/a/b/c/` and a base with no
trailing slash, asserting that every request the panel received stayed below
the configured base.

## Health

`GET panel/api/server/status`, read-only. A mutating endpoint as a health check
would change the thing it measures. `getXrayVersion` is **not** used.

The parser takes the minimum that identifies a 3X-UI status and no more: a
`success: true` envelope whose `obj` is an object carrying `xray`. The anchor
matters because `ServerService.LastStatus()` returns nil until the first
background refresh, which serializes as `"obj": null` under a perfectly
successful envelope — accepting that would report a panel healthy on an empty
answer. `panelVersion` is reported when it passes the allowlist. Every other
field is deliberately unread: coupling health to that large payload would make
an upstream field rename a Nexa outage, and unknown fields stay forward
compatible.

## Transport

All traffic goes through Nexa's `SafeHttpClient`. The adapter is handed a
client already bound to one panel's base URL, timeout budget, response cap and
the installation's URL policy; it cannot construct one, widen one, or address
another host. DNS pinning, the SSRF policy, redirect refusal, TLS verification,
the private CA and the size cap stay centralized there and are not duplicated.
A boundary check fails the build if a provider adapter imports a network client
directly.

Private self-hosted panels remain reachable; this installation's own data
subnet and the hostnames in `DATABASE_URL` and `REDIS_URL` remain denied.

**Redirects are never followed**, so no credential can migrate to another
origin. Tested with a panel that redirects every route to another origin with
the bearer token, cookie and CSRF token pasted into the target: the other
origin receives no request at all.

## Cookies

Ephemeral, adapter-local, and the lifetime of **one probe**. Cookies are
captured from `Set-Cookie`, kept as name and value only, replayed on the
following requests of the same flow, and discarded. `Domain` and `Path` are
dropped deliberately — honouring `Domain` would be the one way a cookie could
widen where it is sent.

Never persisted to the database or disk, never logged, never returned in an
error, never reused across panels, tenants, origins or probe executions. Two
consecutive probes of the same panel mint two different sessions, which the
tests assert from the panel's side.

`Set-Cookie` is exposed on the HTTP result as a narrow typed array rather than
through the flattened header map, because it is the one header that repeats and
a comma-joined string cannot be split back into the cookies that were set.

## Error classification

| Situation                                                              | Kind                                  |
| ---------------------------------------------------------------------- | ------------------------------------- |
| Rejected token, 401/403/404 on the API path, or login `success: false` | `AUTHENTICATION_FAILED`               |
| 2FA enabled with only a username and password                          | `AUTHENTICATION_REQUIRES_INTERACTION` |
| DNS, refused connection, network down                                  | `UNREACHABLE`                         |
| Deadline exceeded                                                      | `TIMEOUT`                             |
| Certificate or handshake                                               | `TLS_FAILED`                          |
| URL policy refusal                                                     | `BLOCKED_TARGET`                      |
| Not JSON, no envelope, `obj` null, no `xray`, oversized                | `MALFORMED_RESPONSE`                  |
| The panel answered with its own failure                                | `PROVIDER_ERROR`                      |
| A credential shape this provider cannot use                            | `UNSUPPORTED_CAPABILITY`              |

These are the existing normalized kinds; only the 2FA case needed a new one.
`AUTHENTICATION_REQUIRES_INTERACTION` and `AUTHENTICATION_FAILED` are both
`AUTH_FAILED` health — the panel answered and did not authenticate — and the
failure column carries which, so the two different jobs read differently.

## Verification

- 42 scenarios against a deterministic fake 3X-UI on a real socket, through
  the real `SafeHttpClient` (`tests/unit/sanaei-adapter.test.ts`).
- 11 end-to-end scenarios against the real service, repository, credential
  store, database and URL policy (`tests/integration/sanaei-panel.test.ts`),
  including credential selection, ciphertext transplant between panels and
  tenants, and the tenant-wide probe budget.
- No real panel is contacted, by design: CI must not depend on somebody's
  installation being up. No user, inbound or live panel state is created or
  mutated anywhere in this phase.

## Known limits

- Only v3.7.0 is claimed. Other releases are not asserted either way.
- mTLS client-certificate authentication exists upstream (`checkAPIAuth` treats
  a verified chain as node-sync) and is not implemented here.
- Session mode cannot authenticate a 2FA-enabled panel, by policy rather than
  by omission.
- A panel that answers the status route correctly but is unwell in ways that
  route does not report will read as healthy; richer health is a later phase.
