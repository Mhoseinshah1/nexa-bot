# R11 A11 — an ended order is answered ON its own payment message, once

Owner request (restated): when an unpaid order **expires** or is **cancelled**, Nexa must EDIT the
order's own payment message — the one with the card number, the copy buttons and the pay/receipt
buttons — into the ended state, instead of sending a new «مهلت این سفارش به پایان رسیده است». The
edited message keeps the order summary (order code, product, amount), loses everything that pays,
and shows «🔁 سفارش دوباره» and «🏠 منوی اصلی». No "no money was taken" line. A new message only
when the original cannot be edited (deleted / too old / unknown id) — and then at most one per
order.

## Why the owner saw three expiry messages (11:09, 11:11, 11:16)

Determined from the code only (no production data read).

**One order, several notices — possible, and fixed here:**

1. `PaymentExpiryService` sent `PAYMENT_EXPIRED` **per payment attempt** (subject = the payment)
   and `ORDER_EXPIRED` per order. An order can hold several PENDING attempts (card-to-card, then a
   gateway, then another gateway, a TonPays-Telegram card attempt …). A gateway attempt's
   deadline is `now + adapter.attemptLifetimeMs` from **its own creation** — not capped by the
   order — and a manual transfer's is capped by the order. So attempts opened at 10:09, 10:11 and
   10:16 lapse at 11:09, 11:11 and 11:16, each with its own new «مهلت پرداخت شما به پایان رسید»
   message, and the order's own notice after the last one. With `sales.order_expiry_minutes`
   above the payment window (allowed: up to 14 days vs ≤ 60 min) even manual attempts diverge.
2. Every tap on a stale pay / confirm / methods button of an order past its deadline (not yet
   swept), and every confirm on a **draft** past its price hold (drafts are never swept), answered
   the bare refusal `bot.order.expired` = «مهلت این سفارش به پایان رسیده است. لطفاً دوباره سفارش
   دهید.», which the wizard sends as a **new** message — three taps, three messages.

The `ORDER_EXPIRED` row itself could never repeat for one order: `customer_notifications_subject_key`
is unique on `(tenant, kind, subject)`.

**Three separate orders, each told once — also possible, order creation unchanged:** every
confirmed pre-invoice is its own order with its own window, and tapping a plan from a new
catalogue message starts a new draft. That is not a bug, so it is left alone (OQ-R11-A11-03).

### Feature commit

- **One expiry notice per order, durable.** `PaymentExpiryService` no longer enqueues
  `PAYMENT_EXPIRED` for a payment that has an order; the order's `ORDER_EXPIRED` is the single
  notice, de-duplicated by the existing unique constraint (not in memory), and the lane's
  `markSendStarted` stamp makes two dispatchers one answer. A top-up payment (no order) keeps
  `PAYMENT_EXPIRED`.
- **The lane edits the order's message.** `CustomerNotificationService.contentOf` renders
  `ORDER_EXPIRED` / `ORDER_CANCELLED` from the ORDER (`order-end-screen.ts`: public code, line
  title, frozen total, and the re-order target) and returns `closesOrder`, so FIX-08's
  `WizardInvoiceScreens.answerOrder` edits it onto the order's latest screen (text + keyboard
  replaced: no card, no copy button, no pay/receipt button). The answerable screens for an ended
  order are FIX-08's set **plus `RECEIPT_WAIT`** (`ORDER_END_ANSWER_STEPS`): an order that
  expired from the receipt prompt had no receipt, so nothing else would ever answer that message.
  `RECEIPT_REVIEW` stays excluded.
  - Edit refused (message deleted / too old): the buttons are cleared best-effort and the screen
    is **sent once**; the row records DELIVERED.
  - «message is not modified» → DELIVERED (existing messenger rule); 429 → retried as the edit,
    no attempt spent; UNKNOWN → UNCONFIRMED, never repeated (existing FIX-08 rules).
  - No message known (an order started in the mini app, or any untracked one): today's single
    message, once.
  - **Nothing is said unless the order is in the kind's ending** (`ORDER_END_STATES`): an order
    paid just before its deadline is never moved to EXPIRED by the sweep (its UPDATE names the
    source state), and even a row that names such an order sends nothing.
- **Stale taps edit, never send.** `order-end-flow.ts` `orderEndedRefusal` / `endedOrderScreen`:
  a `ORDER_EXPIRED` or `ORDER_STATE_INVALID` refusal on confirm (`c:`), wallet (`w:`), methods
  (`pm:`), card-to-card (`m:`) or gateway (`g:`/`gp:`) of an order that has ended (EXPIRED,
  CANCELLED, or still unpaid past its deadline) answers the ended screen landed `CLOSED` on the
  tapped message — it carries nothing that pays, so it cannot be tapped into another one.
- **Cancellation edits the order's message.** `cancelOrder` → `cancelledOrderReply`: after the
  cancellation commits, the order's own message is edited into the cancelled screen
  (`answerOrder`, no settle window — this turn is the writer) and the confirmation question is
  deleted (or its buttons cleared). When the order's message cannot be taken, the question
  message itself is edited into the screen (sent once if that is refused too); the
  `ORDER_CANCELLED` lane fallback stays for a 429.
- **Re-order is read-only.** `orderEndButtons`: «🔁 سفارش دوباره» → `ro:<category>` (new prefix and
  intent `REORDER_CATEGORY`, ungated because it sits on a CLOSED screen; it lists the category's
  plans as a NEW message, the ended screen stays as the record), `cu:` for a custom service, `co:`
  (catalogue) otherwise; «🏠 منوی اصلی» → `mm:`. Nothing is drafted until a plan is tapped, nothing
  ordered until confirmed.
- Gateways checked: card-to-card, TonPays, TonPays-Telegram, NOWPayments, TetraPay, CentralPay,
  Rialit, Stars, custom — all expire through the same sweep, so all now get one order notice. A
  provider-side failure (`GATEWAY_PAYMENT_FAILED`) is a different fact (the order stays payable)
  and is unchanged; a replaced gateway attempt already loses its buttons by edit
  (`WizardInvoiceScreens.retire`), no new message. Mini-app orders: no message id → one send.
- Docs: `docs/project-status.md` gains the binding rule section; `docs/open-questions.md`
  OQ-R11-A11-01..03.

## Decisions

- One expiry notice per order = the order's `ORDER_EXPIRED`; payments of an order are silent
  (owner's "at most one expiry notice per order, ever"). The attempt that lapses while its order is
  still payable gets no message (OQ-R11-A11-01).
- No feature flag: this corrects the existing notification behaviour the owner asked to change.
- No new table/column: the message id per order was already in `telegram_wizards`; no migration,
  no backfill, no customer message from either.
- Re-order for renewals/add-ons opens the catalogue (OQ-R11-A11-02).
- Order creation unchanged (three orders told once each is not a bug; OQ-R11-A11-03).
