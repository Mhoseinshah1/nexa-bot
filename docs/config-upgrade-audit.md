# The configuration upgrade audit

Every variable a production installation runs on, what happens when it is ABSENT,
and whether that absence is safe. Written because an installation that has been
upgraded with `botctl update` since the first release has whatever its original
template wrote and **nothing since** — `botctl update` does not rewrite
`/etc/nexa/nexa.env`, deliberately, so it cannot overwrite an operator's choice.
That policy is correct and it makes "a missing line is safe" a claim about every
variable added after the first install. This is that claim, checked.

The companion tests are `tests/unit/config-upgrade.test.ts`, which parses the
templates real installations were created with through the CURRENT schema, and
`tests/unit/deployment-config.test.ts`, which does the same for the current one.

## The two files, and why they have opposite rules

| File                   | Who writes it                                  | Rule                                                                                                                                           |
| ---------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `/etc/nexa/nexa.env`   | the installer, from `deploy/nexa.env.template` | only what the deployment must DECIDE. Restating a schema default is a second place for it to be wrong.                                         |
| `/etc/nexa/deploy.env` | the installer, then `botctl update`            | what compose interpolates. No secrets: its values reach `docker inspect` and container labels.                                                 |
| `.env.example`         | a contributor, by hand                         | EVERY variable the application reads. It is how somebody discovers what exists, so an omission is a variable nobody finds. Enforced by a test. |

`botctl update` writes `deploy.env` (`NEXA_IMAGE`, `NEXA_EDGE_CONFIG`) and, as of
this audit, removes obsolete keys from `nexa.env`. It changes nothing else in
either.

## Classification

- **A. REQUIRED_EXPLICIT** — a valid installation must carry it deliberately.
- **B. SAFE_SCHEMA_DEFAULT** — may be absent; the default is production-correct.
- **C. OPTIONAL_OPERATOR_CHOICE** — absence is a real, supported, disabled state.
- **D. LEGACY_COMPATIBILITY** — an old spelling that still maps to the current model.
- **E. DERIVED / GENERATED** — generated by the installer, updater or image; not hand-set.
- **F. OBSOLETE** — no longer read, and removed from an existing file.

### A — required explicit

| Variable                                 | Source                                     | Absent on an old install?                                                                                                                                                                                  |
| ---------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                               | template                                   | No — written since the first template. Schema default `development`, which would refuse `AUTH_MODE=none` checks differently; the template has always set it.                                               |
| `DATABASE_URL`                           | installer-generated password               | No. Schema has no default; the process refuses to boot.                                                                                                                                                    |
| `REDIS_URL`                              | installer-generated password               | No. Same.                                                                                                                                                                                                  |
| `WEB_ADMIN_ORIGINS`                      | operator's domain                          | No. Production refuses an empty set.                                                                                                                                                                       |
| `DEPLOYMENT_TOPOLOGY`                    | template                                   | No. `reverse-proxy` is the default and the template restates it because `TRUSTED_PROXY_IPS` is only required under it.                                                                                     |
| `TRUSTED_PROXY_IPS`                      | derived from `NEXA_EDGE_SUBNET` at install | No. Empty under `reverse-proxy` is refused — an empty set would mean the API ignores `X-Forwarded-For` and attributes every request to Caddy.                                                              |
| `SECRETS_KEYS` + `SECRETS_ACTIVE_KEY_ID` | installer-generated                        | Yes on an install older than the keyring release — which has `SECRETS_KEK`/`SECRETS_KEK_ID` instead. See D. One route or the other is required; the schema reports every problem with the keyring at once. |

### B — safe schema default

Everything not named in A, C, D, E or F. The full list is `config.schema.ts`,
which is the authority; what matters for an upgrade is the reasoning, and it is
the same for all of them: the default is declared beside the variable with its
justification, the template never wrote it, and so a fresh install and an
upgraded one resolve the SAME value. `tests/unit/config-upgrade.test.ts` proves
that for the templates real installations were created with rather than asserting
it.

Three groups deserve naming because they are newer than most installations:

| Group                                                                           | Added                  | What absence means                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `WORKER_HEARTBEAT_*`, `PANEL_MONITOR_HEARTBEAT_PATH`, `RECOVERY_HEARTBEAT_PATH` | with each process role | The default path the container healthcheck also defaults to. The healthcheck derives its maximum age from `WORKER_HEARTBEAT_INTERVAL_MS`, and a unit test runs the compose scripts against both the default and the largest interval the schema accepts. All four roles resolve the same values, because compose gives them one `env_file` through `x-app-common`. |
| `NOTIFICATION_*`                                                                | Phase 2                | Dispatch on, two-second interval, bounded back-off. An installation that predates them dispatches notifications on the defaults, which is the behaviour it already had.                                                                                                                                                                                            |
| `BACKUP_*` timeouts and dirs, `RECOVERY_*`                                      | Backup V1 / DR         | The data directories default to the paths compose mounts as named volumes. An installation whose compose predates those volumes does not have the volumes either, and gets them from the release's own compose file at update — the host assets move with the release.                                                                                             |

### C — optional operator choice

Absence is a supported disabled state, and **an upgrade must not change it**.

| Variable                                                | Default    | What absence means                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BACKUP_SCHEDULE_ENABLED`                               | `false`    | No AUTOMATIC backup. Correct: an upgrade that started writing the whole database to a destination nobody configured would be acting on its own initiative. The cost is that an upgraded installation has no scheduled backups and the application cannot say so — which is why `botctl status` now reports it.                                                                                                                                       |
| `BACKUP_TELEGRAM_CHAT_ID` + `BACKUP_TELEGRAM_BOT_TOKEN` | both empty | Delivery not configured. A run still dumps, verifies against a real scratch restore and RETAINS locally; its delivery outcome is `NOT_ATTEMPTED`, which is not a failure. Both set or both unset — a half-configured pair is refused at boot, and `botctl status` reports `HALF configured` before the restart finds out. Nothing in this repository invents a chat id or a token, and the delivery bot is deliberately NOT the customer-facing one. |
| `RECOVERY_UPLOAD_ENABLED`                               | `true`     | On. Switchable off for an installation that would rather restore only from its own retained runs; reported through the capabilities endpoint so the Web Admin says the feature is off rather than offering a button the server refuses.                                                                                                                                                                                                              |
| `PANEL_MONITOR_ENABLED`                                 | `true`     | On. A deliberately disabled monitor stays HEALTHY — it is a process doing nothing on purpose.                                                                                                                                                                                                                                                                                                                                                        |
| `TELEGRAM_WEBHOOK_ENABLED`                              | `false`    | The route does not exist at all. Until Phase 4A there is nothing behind it but `/ping`.                                                                                                                                                                                                                                                                                                                                                              |
| `PANEL_HTTP_CA_FILE`                                    | unset      | System roots only.                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `PANEL_HTTP_DENIED_SUBNETS`                             | empty      | No EXTRA networks refused. The installation's own data network is refused unconditionally and separately — see E.                                                                                                                                                                                                                                                                                                                                    |

### D — legacy compatibility

| Variable                         | Maps to                                              | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SECRETS_KEK` + `SECRETS_KEK_ID` | a one-entry keyring whose only key is the active one | Which is precisely what v1 did. Every installation created before the keyring release has these two and nothing else, and they keep decrypting without anybody hand-editing `nexa.env` or replacing key material. `botctl secrets migrate-config` converts them when the operator is ready; `botctl status` prints which spelling is in force.                                                                                                                                                                             |
| `SECRETS_ACCEPT_V1`              | absent = derived                                     | No default, on purpose: a plain `true` would have made acceptance the thing that happens when nobody decides, and a host installed before the setting existed has no such line. Derived instead — ON for a legacy-spelled configuration, OFF for a canonical one. A v1 ciphertext carries no associated data and so stays transplantable between rows; that is what acceptance costs, and `botctl secrets rewrap` then `disable-v1` is the supported way to stop paying it. **No ordinary update generates key material.** |

### E — derived or generated

| Variable                                      | Written by                                        | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NEXA_IMAGE`                                  | installer, then `botctl update` at commit         | A DIGEST, never a tag.                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `NEXA_EDGE_CONFIG`                            | installer, then `botctl update` at commit         | The fingerprint of the Caddy files on the host. Absent on an installation that predates it; compose defaults it to `unset`, and the first update records a real one. Reconciled on every update, so it cannot go stale.                                                                                                                                                                                                                     |
| `NEXA_DATA_SUBNET`                            | `deploy.env`; compose hands it to the application | ONE value, one source. The panel HTTP policy refuses the installation's own network because compose tells the process which network that is — not because `nexa.env` carries a copy an upgrade would have to keep in step. Absent on an old `deploy.env`; compose's default and the installer's default are now bound by a test, because they were two literals in two files and a disagreement would silently stop the API trusting Caddy. |
| `NEXA_EDGE_SUBNET`                            | `deploy.env`                                      | Same binding. Changing it means changing `TRUSTED_PROXY_IPS` too, and nothing keeps them in step after install — `docs/deployment.md` says so under "Changing the edge subnet".                                                                                                                                                                                                                                                             |
| `BUILD_VERSION`, `BUILD_COMMIT`, `BUILD_TIME` | the IMAGE, at build time                          | See F.                                                                                                                                                                                                                                                                                                                                                                                                                                      |

### F — obsolete, and removed

| Variable                                                    | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BUILD_VERSION`, `BUILD_COMMIT`, `BUILD_TIME` in `nexa.env` | `env_file` beats an image's own ENV, so these lines REPLACE the identity stamped into the release. The FIRST production template wrote all three and the installer substituted `pending` for the commit and the build time — it had built nothing and could not know them. The template stopped writing them the next day, and nothing removed them from a file that already had them. So an installation created then reports the installer's placeholder from `/health/info` for the rest of its life, and an operator cannot tie a running container back to its source. `botctl update` now removes them in one atomic rewrite, non-fatally, and `botctl status` reports them until it has. Safe to remove in the strongest sense available: the schema defaults all three, so the file still boots, and `0.0.0-dev`/`unknown` are true statements where `pending` was a claim that something was about to be filled in. They were never an operator choice — no operator was asked. |

| Could docs claim a different default?                                 | `docs/backup.md` and `docs/deployment.md` were checked against the schema while writing this.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Does `botctl status` expose a disabled capability?                    | It did not. | Are generated assets reconciled on update?                            | Host assets move with the release, and `NEXA_EDGE_CONFIG` is rewritten at commit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Does an old config boot on the current image, for the right reason?   | Yes, and the reason is now a test rather than an argument.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Are deprecated variables mapped or merely tolerated?                  | Mapped. `SECRETS_KEK` aliases to a one-entry keyring; `SECRETS_ACCEPT_V1` is derived from which spelling is present.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Are unknown variables harmless?                                       | The schema ignores keys it does not declare, so a line left over from an earlier release is inert unless it is one the schema DOES declare — which is the F case, and is why F exists rather than being left as "harmless".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## What this audit did NOT do

- It did not append new variables to an existing `nexa.env`. That would destroy
  the distinction between a schema default, an operator choice and a generated
  value, which is the distinction the whole design rests on.
- It did not enable scheduled backups, invent a Telegram destination, or reuse
  the customer-facing bot token.
- It did not rotate or regenerate key material.
- It did not touch the staging host.
