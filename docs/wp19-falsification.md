# WP19 customer service refund request — falsification record

Each rule was reverted against the WP19 branch and the named test file was run: the
integration file against its own test database, the web file in its project. Each mutation
was reverted with `git checkout` before the next one ran. The integration rows are
driven by `scripts/mutate-wp19.py`, which is committed. The web rows, and W19-22b and W19-23 before the driver
learned them, were reverted by hand, one at a time.

W19-47, W19-72 and W19-73 mutate `packages/contracts`. Tests read that package from its
build, so the driver rebuilds it after the edit and again after the restore.

W19-64 survives by design: the sweep's in-flight guard is one of two, and the query's
`not exists` (W19-65) decides first. W19-64b reverts both and the test dies.

The first pass left six mutations alive.

- **W19-02.** No test ever reached an UNKNOWN deletion: a 5xx on an idempotent DELETE is
  retried, not lost. A test now forces the operation to UNKNOWN and asserts that the sweep
  neither credits nor releases.
- **W19-05, W19-06, W19-11, W19-14.** Each reverted one of two guards, and the other one
  decided:
  - W19-05, W19-14: the service's early state check, backed by the repository's
    conditional UPDATE naming `OPEN`;
  - W19-06: the zero check, backed by `refundFitsWithin`;
  - W19-11: the pre-read for an open request, backed by the partial unique index with
    `ON CONFLICT DO NOTHING`.

  Each pair was reverted together (the `b` rows below), and each test dies — except
  W19-14b. The row did not exist until the second Codex review, although this record said
  it did. When it was added, it survived: the rejection has a third guard, the
  `service_refund_requests_rejected_check` CHECK, which refuses a REJECTED row that carries
  an approval. W19-14c reverts all three layers — the driver lifts the CHECK for that one
  row and restores it — and the test dies.

- **W19-01 and W19-22 are pairs since the Codex review of #83.** The sweep query now returns only rows the sweep can decide. So the code guard that refuses a SUCCEEDED deletion whose service did not move, and the credit check that refuses a reservation closed elsewhere, are each backed by a query clause. Reverting either layer alone leaves the other doing the job. Each row therefore reverts the guard and its clause together; W19-22 is renamed W19-22b to say so.
- **W19-02 is a pair since the second Codex review of #83.** The sweep query admits only a
  SUCCEEDED or FAILED/ABANDONED deletion, so adding UNKNOWN to the terminal states alone
  changes nothing. W19-02b reverts that filter and the query's failure clause together.
  W19-02 alone therefore survives, and is recorded SURVIVED; W19-02b is the row that proves
  the rule. (The table said KILLED until the re-run for the fourth review caught it.)
- **W19-28 is superseded.** It held the round-1 order, rejection before the prompt's close.
  That order was the gap the second review found: a prompt cancelled in between still
  rejected. The rejection and the close are now one transaction, held by W19-32 and W19-33.
- **W19-18** survives by design. The approval's operation key names the request, but a
  second approval never reaches the planner with a different key. The request is no longer
  OPEN, and `planWithin` answers any open `TERMINATE` for the service before it reads a
  key. The key is a label, not a rule, and no test is cited for it.
