# برنامهٔ ساده‌سازی import میرزا (مهاجرت یک‌باره)

> وضعیت: برنامهٔ اجرایی شاخهٔ `feat/mirza-import-simplify`، نوشته‌شده پیش از کد. هرجا تصمیمی گرفته شده، دلیلش کنارش آمده است. قاعدهٔ کلی برای هر مورد پیش‌بینی‌نشده این است: گزینه‌ای انتخاب شود که داده از دست نرود، برگشت‌پذیر باشد و پول را دو بار لمس نکند.

## ۱. هدف

مسیر کامل از داخل Web Admin اجرا می‌شود:

**بکاپ میرزا → مبدل → `.nxpkg` → آپلود در Web Admin → verify → dry run → تأیید مالک → import → تطبیق فقط‌خواندنی پنل → لینک به ربات فعال → گزارش «تطابق دقیق» → COMPLETE.**

بعد از آن NEXA بلافاصله قابل استفاده است: هر مشتری، موجودی، سرویس، سفارش، پرداخت، تیکت، معرفی، تخفیف، محصول و نماینده‌ای که در میرزا بود، در جدول‌ها و صفحه‌های **عادی** NEXA هست و علامت «واردشده از میرزا» دارد. صفحه یا کارت جداگانهٔ «میرزا» وجود ندارد. CLI فقط به‌عنوان راه جایگزین می‌ماند.

## ۲. علامت «واردشده از میرزا» و شناسهٔ اصلی

- **ستون مشترک:** هر جدول عادی که ردیف واردشده می‌گیرد، یک ستون `source` با مقدار `NEXA` (پیش‌فرض) یا `MIRZA` و یک ستون `source_ref` (شناسهٔ ردیف در میرزا) می‌گیرد. این دو ستون با CHECK پین می‌شوند:
  - `source = 'NEXA' ⇔ source_ref IS NULL`
  - ترکیب `(tenant, source_ref)` در هر جدول یکتاست، و همین import را idempotent می‌کند.
- **جدول‌ها:** `customers`، `orders`، `payments`، `services`، `tickets`، `ticket_messages`، `referrals`، `discounts`، `products`، `resellers`، و جدول تاریخچهٔ کیف پول (بند ۵-۳).
- **`legacy_import_map`:** برای سازگاری و برای تأیید دوبارهٔ dry run می‌ماند، ولی **منبع حقیقت برای نمایش، علامت `source` روی خود ردیف است**.
- **مقدار جدید یک قرارداد است.** هر مقدار تازه، مثل `PAYMENT_EVIDENCE_KINDS += LEGACY_IMPORT`، ‏`ORDER_ORIGINS += LEGACY_HISTORY` یا `LEDGER_REASONS`، طبق CLAUDE.md در commit جداگانهٔ `packages/contracts` می‌آید و دلیلش در پیام commit نوشته می‌شود.

## ۴. پول: موجودی‌ها و اثبات ایمنی

**قاعده:** موجودی نهایی هر مشتری در NEXA دقیقاً برابر `user.Balance` میرزاست.

1. **ثبت موجودی.** import برای هر مشتری با `Balance ≠ 0` دقیقاً **یک** ردیف `MIGRATION_OPENING_BALANCE` می‌نویسد: CREDIT به اندازهٔ |Balance| برای مثبت و **DEBIT** به اندازهٔ |Balance| برای منفی.
   - CHECK موجود `wallet_entries_migration_opening_shape_check` هر دو جهت را مجاز می‌داند.
   - ایندکس یکتای «یک opening برای هر مشتری» جلوی ردیف دوم را می‌گیرد.
2. **تاریخچه وارد دفتر کل نمی‌شود.** هیچ رکورد تاریخچه‌ای (پرداخت، تراکنش کیف پول، گردونه، سفارش یا تخفیف) در `wallet_entries` نوشته نمی‌شود. پس موجودی که مجموع `wallet_entries` است، از ثبت تاریخچه تغییر نمی‌کند.
3. **موجودی نهایی.** نتیجهٔ دو بند بالا: موجودی = |Balance| × جهت = Balance. ∎
4. **idempotent بودن.**
   - هر ردیف با `(tenant, source_ref)` یکتاست، و opening با `legacy:opening:<tg>` و ایندکس یکتا.
   - اجرای دوباره هیچ ردیف تازه‌ای نمی‌نویسد (`ON CONFLICT DO NOTHING`) و هر ردیف موجود را با بسته مقایسه می‌کند. اگر اختلاف داشت، import با `IMPORT_DIVERGED` متوقف می‌شود.
5. **موجودی منفی خرید را مسدود می‌کند.**
   - **خرید از کیف پول** امروز هم با `canCover` و صفر بودن `creditAllowanceOf` مسدود است.
   - **قاعدهٔ تازه:** وقتی موجودی کیف پول **منفی** است، **هر** خرید (با درگاه، کارت‌به‌کارت یا کیف پول) در confirmation رد می‌شود (کد تازهٔ `commerce.wallet_negative_top_up_required`، در commit جداگانهٔ contract) تا مشتری شارژ کند.
   - شارژ همیشه مجاز است. شارژ با بدهی جمع می‌شود: این همان «وصول» است که مالک خواسته.
   - **نماینده‌ها هم همین قاعده را دارند** (تصمیم مالک ۲۰۲۶-۱۰-۱۸). موجودی منفی نماینده، چه از میرزا آمده باشد و چه بدهی قدیمی از اعتبار نماینده‌ای که ۲۰۲۶-۱۰-۰۱ حذف شد، تا شارژ نشود جلوی هر خریدی را می‌گیرد. قاعدهٔ قدیمی «هرگز وصول نمی‌شود» جایگزین شده است: بدهی همچنان شارژ یا کهنه نمی‌شود، ولی تا شارژ نشود هیچ فروش تازه‌ای انجام نمی‌شود.
6. **حذف مسیر بررسی بدهی.**
   - `holdNegative`، جدول `legacy_wallet_debts`، صفحهٔ `/legacy-debts` و کارت بدهی Customer 360 دیگر نوشته یا نمایش داده نمی‌شوند.
   - جدول و migrationهایش برای بازگشت‌پذیری **حذف (drop) نمی‌شوند**؛ فقط دیگر چیزی در آن‌ها نوشته نمی‌شود.
   - تست مرزی `legacy-wallet-debts-boundary` با تست تازهٔ «موجودی منفی DEBIT می‌شود» جایگزین می‌شود.
7. **نماینده‌ها.** `maxbuyagent` هرگز وارد کیف پول نمی‌شود. تست: نماینده‌ای با `maxbuyagent > 0` و `Balance = 0` به موجودی ۰ می‌رسد.
8. **اعتبار نماینده.** CLAUDE.md «اعتبار نماینده» را حذف‌شده می‌داند و این برنامه آن را برنمی‌گرداند. `creditAllowanceOf` صفر می‌ماند و خرید هرگز کیف پول را زیر صفر نمی‌برد. فقط موجودی منفیِ **واردشده** وجود دارد.

## ۵. تاریخچه: هیچ اثری ندارد و هیچ کاری راه نمی‌اندازد

1. **درج مستقیم.** ردیف‌های تاریخی مستقیم در repositoryهای import درج می‌شوند، نه از مسیر سرویس‌های تجاری. پس هیچ رویداد outbox، اعلان، پیام یا یادآوری ساخته نمی‌شود.
2. **مسیرهای خودکار به ردیف `MIRZA` دست نمی‌زنند.** sweepها و حلقه‌ها ردیف‌های `source = 'MIRZA'` در وضعیت تاریخی را نادیده می‌گیرند:
   - **سفارش‌ها:** PAID یا CANCELLED هستند و `order_cashback` و `order_referral_commissions` ندارند. پس cashback و پورسانت هرگز «earn» نمی‌شوند.
   - **پرداخت‌ها:** در وضعیت پایانی‌اند (CONFIRMED، FAILED، CANCELLED یا EXPIRED). پس حلقه‌های انقضا و استعلام درگاه، که فقط PENDING را می‌بینند، به آن‌ها دست نمی‌زنند. پرداخت میرزا که PENDING مانده، به‌عنوان EXPIRED تاریخی وارد می‌شود (تصمیم: هرگز پرداخت باز تاریخی نداریم).
   - **معرفی‌ها:** با `rewarded_at` یا علامت «تاریخی» وارد می‌شوند. سرویس هدیهٔ ثبت‌نام ردیف `source=MIRZA` را واجد شرایط نمی‌داند (فیلتر تازه، با تست).
   - **تیکت‌ها:** با وضعیت پایانی و بدون رویداد وارد می‌شوند.
3. **تاریخچهٔ کیف پول** در جدول `wallet_history_imports` نوشته می‌شود و API تاریخچهٔ کیف پول و صفحهٔ عادی «تاریخچهٔ کیف پول» آن را **کنار** ردیف‌های دفتر کل نشان می‌دهند، با برچسب «از میرزا».
   - این ردیف‌ها هرگز در مجموع موجودی حساب نمی‌شوند.
   - **تصمیم:** این تنها جایی است که «همان جدول» عملاً یک جدول خواهر می‌شود، چون نوشتن تاریخچه در `wallet_entries` یا موجودی را تغییر می‌دهد یا به یک ردیف جبرانی نیاز دارد، و این یعنی دو بار لمس پول.
4. **گزارش‌های مالی.** گزارش درآمد NEXA ردیف‌های `source=MIRZA` را جدا نشان می‌دهد («درآمد تاریخی میرزا») و در درآمد NEXA جمع نمی‌زند. پس هیچ عددی دو بار حساب نمی‌شود.

## ۶. سرویس‌ها و تطبیق فقط‌خواندنی پنل

- **مجموعهٔ تطبیق.** همهٔ فاکتورها با پنل تطبیق داده می‌شوند، نه فقط فاکتورهای با وضعیت «زنده». موجودی پنل با خواندن فقط‌خواندنی (RickPanel inventory با دو walk) به دست می‌آید.
- **حساب روی پنل باشد** (با هر وضعیتی: فعال، منقضی، محدود یا غیرفعال): یک سرویس واقعی NEXA ساخته می‌شود با مقادیر پنل (حجم، مصرف، انقضا، وضعیت). همان مسیر adopt فعلی است، با وضعیت‌های بیشتر:
  - `on_hold` و ناشناخته به ACTIVE نگاشت می‌شوند و علامت «بررسی» می‌گیرند (تصمیم: سرویس از دست نرود)؛
  - limited ACTIVE می‌شود؛
  - disabled SUSPENDED می‌شود؛
  - expired EXPIRED می‌شود.
- **محصول هرگز مانع وصل‌شدن نیست** (قانون مالک ۲۰۲۶-۱۰-۱۸): هر سرویسی که حسابش روی یک پنل وصل‌شده هست، در همان import یک‌کلیکی به مشتری‌اش وصل می‌شود؛ محصول ناشناخته، حذف‌شده، نگاشت‌نشده یا بدون تعرفهٔ فعلی جلوی آن را نمی‌گیرد. سفارش این سرویس فقط برای ناوبری به محصول پنهانِ شکلِ همان فاکتور اشاره می‌کند (مقدار: صفر)؛ حجم، مصرف، انقضا و وضعیت از پنل می‌آیند و نام و قیمت اصلی میرزا در بایگانی فاکتور می‌ماند. فقط شکلی که اصلاً خوانا نیست (حجم یا مدت نامعتبر) برای بررسی می‌ماند، چون محصولی ساخته نمی‌شود.
- **تمدید سرویس واردشده:** فهرست پلن‌های قابل فروشِ فعلیِ پنلِ همان سرویس نشان داده می‌شود (هم‌شکل با سرویس: سرویس زمان‌دار با پلن زمان‌دار)، نه محصول اصلی. اگر پنل پلنی نداشته باشد، پیام فارسی «پلنی برای تمدید نیست» (`bot.service.renew_no_plan`) نشان داده می‌شود، نه خطا. هیچ تصمیم جداگانه برای هر محصول، صفحهٔ `/legacy-products`، تأیید دوم یا بارگذاری دوباره لازم نیست.
- **فاکتور بدون `code_panel`:** نام کاربری در موجودی همهٔ پنل‌های وصل‌شده جست‌وجو می‌شود: دقیقاً یک پنل ← روی همان پنل وصل می‌شود؛ هیچ پنلی ← پایان‌یافته و بایگانی، دقیقاً همان مسیر کد پنل نگاشت‌نشده (`PANEL_UNMAPPED`): نتیجهٔ `NO_PANEL`، ردیف بایگانی فاکتور و بدون سرویس، چون سرویس پایان‌یافته باید پنلی داشته باشد و پنلی حدس زده نمی‌شود؛ چند پنل ← در صف بررسی می‌ماند (`AMBIGUOUS_PANEL`).
- **حساب روی پنل نباشد:** سرویس NEXA با وضعیت **TERMINATED** («پایان‌یافته») ساخته می‌شود؛ به مشتری و سفارشش وصل است و **هرگز provision نمی‌شود** (هیچ `provisioning_operation`ی نوشته نمی‌شود).
  - تداخل نام کاربری: محدودیت یکتای `services_panel_provider_username_key` فقط برای سرویس‌های غیر TERMINATED اعمال خواهد شد (partial index، تصمیم: نام یک حساب پایان‌یافته آزاد است؛ با تست).
  - `service_username_reservations` برای سرویس TERMINATED نوشته نمی‌شود.
- **فاکتور تست:** TERMINATED می‌شود، با علامت `is_test`.
- **فاکتور پرداخت‌نشده** (تصمیم مالک ۲۰۲۶-۱۰-۱۸): فاکتوری با وضعیت `unpaid`، `Unsuccessful` یا بدون وضعیت، سرویس نمی‌شود ولی یک سفارش `LEGACY_HISTORY` با `source = 'MIRZA'` می‌شود. شناسهٔ آن `invoice-never-paid:<id_invoice>` است، و تاریخ و مبلغ اصلی را نگه می‌دارد.
  - نگاشت وضعیت: `unpaid` به `EXPIRED`، `Unsuccessful` به `CANCELLED`، و بدون وضعیت به `EXPIRED`. نگاشت آخری حدس است و در کد هم همین گفته شده.
  - هیچ پرداخت، ورودی کیف پول، سرویس، اعلان یا رویدادی ساخته نمی‌شود، و این سفارش‌ها در هیچ گزارش فروشی شمرده نمی‌شوند.
  - در گزارش تطابق دقیق، این سفارش‌ها ردیف NEXA حساب می‌شوند. مبلغشان در دستهٔ توضیح‌داده‌شدهٔ `NEVER_PAID_AMOUNT_NOT_REVENUE` می‌آید، تا هرگز با پول پرداخت‌شده جمع نشود.
  - فقط فاکتوری که نوشتن سفارشش بدون ساختن داده ممکن نیست، شکاف شمرده‌شده می‌ماند: کلید نامعتبر، مالکی که وارد نشده، پنل نامشخص یا نگاشت‌نشده، شکل ناخوانا، یا شکلی که هیچ محصول پنهانی برایش ساخته نشده است.
- **یادآوری‌ها:** برای سرویس‌های واردشده آستانه‌های گذشته seed می‌شوند (رفتار فعلی adopt)، تا هیچ یادآوری عقب‌افتاده‌ای فرستاده نشود.
- **هیچ نوشتنی روی پنل.** تست موجود `refusedWrites = 0` می‌ماند، و تست تازهٔ end-to-end صفر بودن نوشتن روی پنل را پین می‌کند.

## ۷. محصولات، نماینده‌ها و تخفیف‌ها (خودکار)

- محصولات: بند ۳. مسیر «بررسی محصول» (`/legacy-products`) حذف می‌شود؛ محصول مستقیم ساخته می‌شود و بعداً در صفحهٔ عادی محصولات ویرایش می‌شود.
- نماینده‌ها:
  - ردیف `resellers` با وضعیت ACTIVE ساخته می‌شود.
  - سطح و قیمت‌های اختصاصی از `tier_prices` تبدیل می‌شوند. جایی که معنای قیمت ثابت نشده (`price_semantics: UNKNOWN`)، مقدار خام در `source_detail` می‌ماند و نماینده با قیمت عادی شروع می‌کند (تصمیم: قیمتی که اثبات نشده اعمال نمی‌شود).
  - `maxbuyagent` فقط در تاریخچهٔ واردکردن (خام) می‌ماند؛ هیچ ستون یا فیلد NEXA آن را نگه نمی‌دارد.
- کدهای تخفیف: همه **INACTIVE**.

## ۸. Web Admin

- **صفحهٔ «انتقال از میرزا»** (همان بخش بازیابی فعلی، کامل‌شده) گام‌ها را با شمارندهٔ هرکدام نشان می‌دهد:
  - آپلود و کلید
  - verify
  - نگاشت پنل
  - dry run
  - تأیید مالک
  - بکاپ محافظ
  - import
  - تطبیق پنل و ساخت سرویس‌ها
  - محصولات و نماینده‌ها
  - **لینک مشتریان به ربات فعال**، با شمارنده
  - گزارش تطابق دقیق
  - COMPLETE
- **لینک به ربات فعال:** گام خودکار بعد از import است، با همان سرویس امن (`customers-link-bot`): فقط ربات ACTIVE، یک ربات برای هر tenant، بررسی فعال بودن نصب.
- **گزارش «تطابق دقیق»:** برای هر جدول میرزا تعداد ردیف و جمع مبالغ در میرزا و در NEXA، و سرویس‌های روی پنل در برابر سرویس‌های adopt‌شده. هر اختلاف برجسته می‌شود و دلیلش را دارد. import فقط وقتی **COMPLETE** می‌شود که هیچ اختلاف بدون دلیلی نماند.
- **حذف از رابط:**
  - صفحه‌ها: `/legacy-records`، `/legacy-invoices`، `/legacy-debts`، `/legacy-products`، `/legacy-services`
  - کارت‌های Customer 360: سوابق میرزا، فاکتورهای میرزا، سوابق مالی و بدهی میرزا
  - کارت «سوابق میرزا» روی صفحهٔ سرویس
  - نشانی‌های ناوبری مربوط
  - API و کد بایگانی‌ای که فقط این‌ها را تغذیه می‌کرد
- **نگه داشتن:** verify، dry run، تأیید (cutover)، تطبیق، پنل فقط‌خواندنی، بکاپ و گزارش تطابق.
- **علامت «از میرزا»:** در صفحه‌های عادی (مشتریان، سرویس‌ها، سفارش‌ها، پرداخت‌ها، تیکت‌ها، تخفیف‌ها، محصولات و نماینده‌ها) یک نشان کوچک و یک فیلتر «منبع» اضافه می‌شود.

## ۹. تست‌های اجباری

1. تاریخچه هرگز موجودی را تغییر نمی‌دهد: مجموع `wallet_entries` پیش و پس از ثبت تاریخچه برابر است.
2. موجودی نهایی هر مشتری برابر `Balance` میرزاست؛ برای هر مشتری بکاپ مصنوعی بررسی می‌شود: مثبت، منفی و صفر.
3. موجودی منفی خرید را مسدود می‌کند (کیف پول، درگاه و کارت‌به‌کارت) و بعد از شارژ کافی، خرید مجاز می‌شود.
4. هیچ نوشتنی روی پنل انجام نمی‌شود: `refusedWrites = 0` و فقط درخواست‌های GET و token.
5. اجرای دوبارهٔ import هیچ چیز را تغییر نمی‌دهد: تعداد و جمع همهٔ جدول‌ها برابر می‌ماند.
6. نماینده‌ای با `maxbuyagent > 0` و `Balance = 0` به موجودی ۰ می‌رسد.
7. ردیف‌های تاریخی هیچ outbox، اعلان، پورسانت، cashback، هدیهٔ ثبت‌نام، provision یا یادآوری عقب‌افتاده‌ای نمی‌سازند.
8. تست end-to-end: یک بکاپ مصنوعی میرزا از مبدل و `.nxpkg` می‌گذرد و از مسیر Web Admin import می‌شود. گزارش تطابق دقیق بدون اختلاف است و وضعیت COMPLETE می‌شود.

## ۱۰. ترتیب اجرا (هر مرحله با CI سبز)

1. پول: DEBIT برای منفی، حذف مسیر بدهی، مسدود شدن خرید با موجودی منفی، و قرارداد.
2. علامت `source` و `source_ref` روی جدول‌های عادی (migration).
3. سرویس‌ها و تطبیق پنل: همهٔ فاکتورها، TERMINATED برای حساب‌های غایب، فاکتورهای تست.
4. تاریخچه در جدول‌های عادی: سفارش، پرداخت، تیکت، معرفی، تخفیف، گردونه و کیف پول.
5. محصولات، نماینده‌ها و تخفیف‌ها.
6. Web Admin: گام لینک ربات، گزارش تطابق، علامت‌ها، حذف صفحه‌ها و کارت‌های میرزا.
7. تست end-to-end و بازبینی نهایی.
